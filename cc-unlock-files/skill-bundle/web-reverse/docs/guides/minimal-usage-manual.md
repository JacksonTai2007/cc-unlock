# 最小使用手册

本手册只保留新方案下最重要的使用习惯。

## 1. 先写清六件事

给模型的提示词优先写：

- 任务目标
- 验收标准
- 已知难点
- 页面 / 接口 / 样本
- 当前主模式偏好（请求验收 / 浏览器复用 / 本地复现 / 纯算法）
- 是否允许主动全网搜索纠偏（`mcp__web-search__search_bing`）

不要优先要求：

- 当前阶段
- 产物落点
- 下一步计划

因为这会诱导模型先汇报而不是先执行。

## 2. 默认持续推进

除非出现以下情况，否则模型不应停下来等你再发“继续”：

- 需要你登录 / 验证码 / 补样本
- 存在高风险副作用
- 路线发生重要偏差，需要你确认
- 已完成可验证交付

## 3. 先定交付梯度，再决定要不要深拆

- 只要浏览器内请求成功：先把浏览器 harness 跑稳
- 只要 clear boundary：先做内容层验证，不要把容器层当完成
- 只有明确要求脱离浏览器、或前几层都不足时，才进入纯算法提取
- 如果后来发现当前梯度选高了，要敢于降级，不要为了“面子上更完整”继续高成本深拆

## 4. 看重验收，不看重研究型收敛

真正的推进是：

- 请求更接近成功
- 本地复现更接近可运行
- 解密结果更接近可验证
- 更接近纯算法迁移
- 外部搜索把路线纠正得更准确

不是：

- 更多 slot / selector / patch family 已解释清楚
- 更多内部差异已收敛
- 搜到更多网页但没有回到主线

## 5. 默认两轮没逼近验收就换路线，深层专题按 permit 例外处理

如果模型在同一路线默认连续两轮只是拿到更细的内部解释，而没有逼近最终交付，就应强制 pivot，并写 retrospective。  
但若命中 VM / WASM / 混淆，且当前 microRoute 已开启 `deepDivePermit`，则应改看：
- 是否仍在新增高价值证据
- 是否仍在 `maxRounds` 预算内
- 是否尚未命中 `exitCondition`

## 6. 搜索用于纠偏，不用于交差

如果进行了全网搜索（`mcp__web-search__search_bing`），必须要求模型：

- 记录查询与来源
- 说明采纳 / 拒绝理由
- 回到 entrypoint loop
- 用新的 probe 验证搜索结论

## 7. 结论要和证据强度匹配

续跑任务建议顺手要求模型显式写出：

- `activeEntrypoint / entrypointStatus`
- `execution.nextExecutableAction`
- `acceptanceGap / nextEvidenceGate`

这样可以避免只看到“当前阶段是 Capture”，却看不到真正下一步要做什么。

至少区分：

- `provisional`
- `route-ready`
- `acceptance-ready`
- `delivered`

不要把“看起来差不多成功了”当正式结论。

简单理解：

- `provisional` = 线索到了，但还不能拿去当结果
- `route-ready` = 足以指导下一轮
- `acceptance-ready` = 已经碰到验收边界
- `delivered` = 验证和交付都完成了

## 8. 不要误把普通自动化测试当成逆向任务

以下通常不属于本 skill：

- 普通 Playwright / Puppeteer UI smoke test
- 页面可见元素断言
- 常规登录后菜单 / 按钮 / 头像检查

只有当浏览器自动化是为了**复用受保护运行时、维持会话态、截获签名/解密链、或逼近逆向交付**时，才属于本 skill 范围。

## 9. 一个好提示 vs 一个坏提示

- 好提示：`继续这个已有 task-local。浏览器 baseline 成功，但本地 signer rejected。目标是先在 Playwright harness 内稳定 accepted request，再决定是否需要纯算法迁移。`
- 坏提示：`帮我看看这个项目，顺便继续分析一下。`

差别在于：
- 好提示明确了验收目标
- 好提示明确了当前交付梯度
- 好提示避免把模型引向宽泛汇报
