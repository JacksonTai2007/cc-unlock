# Composite Protection Playbook

Version: 1

适用场景：目标使用多层保护手段的组合，如 Anti-debug + Anti-tamper + Dynamic code + JSVMP + WASM + Fingerprint 等协同工作，且保护层之间存在依赖关系、触发顺序和相互校验。

## 核心定位

现代前端保护几乎不存在单一手段。常见组合：

| 组合层级 | 典型手段 | 作用 |
|---------|---------|------|
| L1 反调试 | debugger、timing、size、toString | 阻止调试、增加分析成本 |
| L2 完整性 | self-check、hook seal、CSP、SRI | 检测篡改、阻止注入 |
| L3 动态代码 | eval、Function、blob、动态 import | 隐藏真实代码、延迟暴露 |
| L4 VM 保护 | JSVMP、自定义解释器 | 核心算法虚拟化 |
| L5 WASM | 加密/哈希/签名落 WASM | 算法下沉到二进制 |
| L6 指纹 | 环境采集、自动化检测 | 绑定运行环境 |
| L7 风控 | challenge、token、行为遥测 | 服务端校验 |

这些层级之间不是简单的"叠加"，而是存在：

- **触发依赖**：上层保护被绕过可能触发下层保护升级
- **状态共享**：多层保护共享同一套环境状态或会话状态
- **交叉校验**：A 层的完整性校验包含 B 层代码的哈希
- **级联失效**：某一层异常可能导致后续多层连锁失败

## 组合模式识别

### 模式 1：顺序触发链

**特征：**
- 页面加载 → 反调试初始化 → 完整性自检 → 动态代码解包 → VM 初始化 → WASM 加载 → 指纹采集 → 业务逻辑

**分析策略：**
1. 用 timeline 记录每层保护的触发时机
2. 确认是否有"前一层失败则后一层不执行"的依赖
3. 定位第一层真实阻塞点（往往不是最后一层报错的位置）

### 模式 2：交叉校验环

**特征：**
- 反调试代码的完整性被 anti-tamper 校验
- anti-tamper 代码本身运行在 VM 中
- VM 的字节码解码依赖 WASM 提供的解密函数
- WASM 的加载需要指纹采集通过

**分析策略：**
1. 画出"谁校验谁"的依赖图
2. 识别环状依赖（A 依赖 B，B 依赖 C，C 依赖 A）
3. 找到最小破环点（打破哪个依赖能让分析继续）
4. 评估破环的副作用（是否会触发其他校验失败）

### 模式 3：环境绑定链

**特征：**
- 指纹采集 → 环境值进入 VMP → VMP 调用 WASM → WASM 输出进入签名
- 环境值的变化会沿链传播，影响最终输出

**分析策略：**
1. 建立从"环境读取"到"最终输出"的完整链
2. 确认链上每个环节的变换和传递方式
3. 评估"补环境"需要覆盖的最小集合
4. 参考 `env-as-algorithm-input-playbook.md`

### 模式 4：降级/升级策略

**特征：**
- 若指纹采集异常，切换到更严格的 challenge
- 若反调试触发，加载更混淆的 VM 字节码
- 若 WASM 加载失败，回退到 JS 实现的降级算法

**分析策略：**
1. 识别正常路径和降级路径
2. 确认触发降级的条件
3. 评估降级路径是否更容易分析（有时降级路径是突破口）
4. 确认升级路径是否会引入新的保护层级

## 级联诊断方法

当遇到"绕过一层后另一层失败"时，使用以下诊断流程：

### 步骤 1：建立保护层级图

```
[Anti-debug] --triggers--> [Anti-tamper] --triggers--> [Dynamic Code]
     |                           |                           |
     |--shares-state-with-------|                           |
     |                                                       |
     |--triggers-on-failure-------------------------------->|
                              |
                              v
                        [JSVMP] --calls--> [WASM] --reads--> [Fingerprint]
                              |                                        |
                              |--produces---------------------------->|
                                                                     v
                                                              [Signature]
```

### 步骤 2：定位 first failure

- 不是看"最后哪里报错"，而是看"最先哪里异常"
- 使用 timeline 追踪：正常流程中每个保护层的通过时间
- 对比绕过后的 timeline，找出第一个偏离正常的点

### 步骤 3：判断 failure 类型

| 类型 | 特征 | 处理策略 |
|------|------|---------|
| 触发依赖失败 | 绕过 A 后 B 不再触发，导致 C 缺少输入 | 模拟 A 的"正常通过"信号 |
| 完整性校验失败 | 绕过 A 时修改了代码，B 的完整性校验检测到 | 精确 patch，只改最小必要 |
| 状态不一致 | A 和 B 共享状态，绕过 A 后状态不对 | 同步共享状态 |
| 环境漂移 | A 的绕过引入了环境差异，C 检测到 | 控制环境一致性 |

### 步骤 4：选择破环策略

| 策略 | 适用场景 | 风险 |
|------|---------|------|
| 最小 patch | 精确绕过某层，不影响其他层 | 需要深入理解目标结构 |
| 信号伪造 | 模拟某层的"通过"信号 | 可能触发更深层的校验 |
| 降级诱导 | 诱导目标进入降级路径 | 降级路径可能功能不完整 |
| 黑盒复用 | 整体绕过，只关注输入输出 | 无法纯算法提取 |
| 浏览器可控复用 | 在浏览器内精细操控 | 需要维持会话态 |

## 商业保护识别

在组合保护分析的早期，应先识别是否命中商业化保护方案（见 `commercial-protection-playbook.md`）：

1. 检查全局对象（`window.bmak`、`window.DataDome`、`window.turnstile` 等）
2. 检查Cookie特征（`_abck`、`datadome`、`__cf_bm` 等）
3. 检查脚本URL和响应头标识
4. 快速识别保护提供商可大幅缩小分析范围

常见商业保护的组合特征：
- **Akamai**: 高频行为遥测 + 深度指纹 + 服务端ML
- **Cloudflare**: Challenge编排 + Turnstile + 基础指纹
- **DataDome**: 严格自动化检测 + 详细环境采集 + 强会话绑定
- **PerimeterX**: 多层自校验 + toString检测 + 请求签名
- **Kasada**: WASM核心 + JSVMP + 动态令牌

## 传输层指纹

如果前端保护已全部绕过但请求仍被拒绝，检查传输层指纹（见 `tls-http-fingerprint-playbook.md`）：

- TLS JA3/JA4指纹是否匹配目标浏览器
- HTTP/2 SETTINGS帧是否与浏览器一致
- HTTP Header顺序和组合是否异常

## 跨专题执行策略

当任务命中多个保护专题时，执行顺序建议：

### 阶段 1：侦察（Observe）

1. 快速扫描所有保护层的存在性
2. 建立保护层 timeline（谁在先、谁在后）
3. 识别明显的组合模式

### 阶段 2：分层突破（Capture）

按以下优先级选择突破口：

1. **最高优先级**：能直接拿到目标输出（签名/请求）的层
   - 若 sign 在 WASM 中，优先突破 WASM
   - 若 sign 在 VMP 中，优先突破 VMP
2. **次高优先级**：能稳定复现目标输出的层
   - 黑盒复用 WASM export
   - 浏览器内可控复用
3. **中等优先级**：能简化后续分析的层
   - 先反调试（避免调试中断）
   - 再动态代码（拿到明文代码）
4. **低优先级**：纯研究性质的理解
   - 完整还原 anti-tamper 校验逻辑
   - 逐条解释 VMP opcode

### 阶段 3：联动验证（Rebuild + Patch）

1. 每突破一层，验证后续层是否仍正常
2. 若后续层异常，使用级联诊断定位问题
3. 不要追求"完全还原每一层"，追求"能稳定拿到目标输出"

## 常见组合场景

### 场景 A：Anti-debug + Anti-tamper 联动

**特征：**
- 反调试代码本身被完整性校验保护
- 篡改反调试代码会触发 anti-tamper

**策略：**
- 优先使用 preload 注入，避免运行时修改已加载代码
- 若 preload 不可行，精确 patch anti-tamper 的校验目标

### 场景 B：Dynamic code + JSVMP 嵌套

**特征：**
- 动态代码解包后包含 VM 初始化逻辑
- VM 字节码可能继续通过动态代码加载

**策略：**
- hook `eval` / `Function` 捕获动态代码明文
- 在动态代码中定位 VM constructor
- 追踪 VM 字节码的所有来源（可能有多段）

### 场景 C：JSVMP + WASM + Fingerprint 绑定

**特征：**
- VMP 读取环境值 → 调用 WASM → WASM 计算签名
- 环境值同时参与指纹采集和算法运算

**策略：**
- 参考 `wasm-jsvmp-bridge-playbook.md`
- 参考 `env-as-algorithm-input-playbook.md`
- 建立"环境值 → VMP → WASM → 签名"的完整链
- 验证环境值修改对签名的影响

### 场景 D：Challenge + Token + Signer state 循环

**特征：**
- challenge 成功生成 token
- token 进入 signer state
- signer state 参与请求签名
- 请求失败触发新 challenge

**策略：**
- 参考 `challenge-orchestration-playbook.md`
- 参考 `signature-playbook.md`
- 建立 token 生命周期图
- 区分"token 失效"和"签名错误"两种失败模式

## 交付要求

命中组合保护时，除了各专题的独立交付物，还需补充：

- `run/composite-protection-map.md`
  - 保护层级图
  - 触发顺序 timeline
  - 依赖关系（谁校验谁、谁触发谁）
  - 状态共享点
  - 破环策略和已执行的绕过
  - 残余风险和未解层级

- `report.md` 中必须包含：
  - 组合保护模式判定
  - 各层级的状态和绕过情况
  - 级联诊断结论
  - 最小可行突破路径

---

## 禁止事项

- 孤立分析每个保护层，不建立层间关系图
- 绕过一层后就认为"保护已解决"，忽略级联影响
- 在不了解组合模式的情况下，大面积 patch 全局对象
- 把"某层绕过失败"直接等同于"该层技术太难"，而不诊断是否是上层影响
- 追求"完全还原每一层"而忽视最终验收目标
